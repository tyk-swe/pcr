# Add a Scope time Window as scope v2, keeping v1 documents valid

An engagement Scope already narrows destinations, policy opt-ins and budgets, but it says nothing about when live work may run. Engagements are usually authorised for a stated period, and an operator who reuses last week's Scope file today gets no signal from the tool that the authorisation window has passed. A time bound belongs in the Scope for the same reason the destination bounds do, because it is part of the operator-declared boundary of the engagement rather than a per-command preference.

We therefore add `packetcraftr.scope/v2`, which is the v1 document plus optional `not_before_unix_seconds` and `not_after_unix_seconds` bounds forming one half-open Window, where the start is included and the end is excluded. A v2 document must declare at least one bound, and a v1 document that carries either field is rejected, so the version in the document always says which fields may appear. Existing v1 documents stay valid with unchanged meaning and unchanged canonical digests, because engagement records and Evidence bundles already name Scopes by digest. The Window only narrows, like every other Scope field. Narrowing a Policy that already carries a Window intersects the two, and an empty intersection denies every operation instead of widening to either side.

The Window is checked when an operation is admitted, at the same place budgets are authorised, and when a live capture is planned. Destination authorisation and per-message reauthorisation stay spatial and time-free, and admission judges the Window at the instant the operation was admitted, so an operation admitted inside the Window is not retroactively failed if it runs past the end. Target resolution takes the admission instant from the client's injected clock rather than reading host time a second time, so a deterministic clock decides admission and resolution the same way. Operators who need a hard stop already have per-operation duration limits, and combining the two is their choice. Parsing a Scope never depends on the current time, so `network preflight` can validate and report an inactive Window instead of rejecting the document, and a pre-epoch system clock fails closed whenever a Window is present.

We considered adding the fields to v1 instead. That would make documents the current schema rejects as unknown fields valid under the same identifier, and a reader could no longer tell from the schema string alone whether a Window may be present. We also considered a repeating daily schedule, and rejected it for this step because engagements state one authorised period far more often than a recurring one, and a single interval can be intersected, digested and explained without a calendar model. If recurring windows are ever needed they can take the next Scope version with their own schema and tests.
