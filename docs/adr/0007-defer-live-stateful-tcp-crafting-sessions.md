# Defer live stateful TCP crafting sessions until a cooperating peer exists

A live session that maintains sequence, acknowledgement, and window state while an operator injects hand built segments is the largest request behind the red team improvements. The building blocks partly exist. Packet build already expands an offline synthetic TCP conversation with a handshake, segmentation, acknowledgements, and a close, and exchange already correlates replies to sent packets under traffic policy. Neither owns a live TCP state machine.

Three obstacles keep this out of the current work. The host kernel also owns TCP state for the same addresses and ports, so it can answer with resets the tool did not send, and suppressing that is platform specific firewall work outside the native provider boundary. A session that lasts across operator input also needs a lifetime, cancellation, and evidence model that the one shot operation deadline and budget admission in the client do not have yet. Most importantly, a crafted session against an arbitrary peer proves little when it breaks, because the peer, a middlebox, the host stack, and the tool can each be the reason. The differential work solved the same problem with a cooperating Responder, and a TCP session needs the equivalent cooperating peer before its results can be reported as findings.

We therefore do not build a live stateful TCP session now. The next step, if it is taken, is a cooperating TCP peer that logs the segments it receives, after which a bounded session engine can be designed against paired evidence. Until then, offline synthetic conversations, exchange, scan, and differential Campaigns cover the provable cases, and ordinary connect based tools cover unmodified TCP.
