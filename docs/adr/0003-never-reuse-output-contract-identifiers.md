# Never reuse an output contract identifier

Every JSON and NDJSON envelope names its output contract in the `schema` field, and consumers pick a schema by that identifier alone. Commit 834d8466 reset the contract to `packetcraftr.output/v1` after v2 through v18 had already been used, so the reset baseline shared its identifier with six released schemas from 0.3.0 to 0.5.0-beta.2, each with different content. A `packetcraftr.output/v1` document no longer tells a consumer which schema it follows. We therefore emit `packetcraftr.output/v19`, the first identifier that appears nowhere in this repository's history, and treat output identifiers as immutable. Once an identifier lands on the main branch or in a release it names one contract line, and a later contract takes the next unused number instead of resetting or reusing an old one.

The constant `OUTPUT_SCHEMA` in `crates/packetcraftr-core/src/security.rs` is the only owner of the emitted identifier. The CLI's `output::contract::SCHEMA` re-exports it for emission, and the scan-diff and report input checks read the same constant, together with `AMBIGUOUS_OUTPUT_SCHEMA` for the rejected v1 identity. `scripts/check_output_schema.py` fails when the runtime constant, the schema's `$id` and envelope `const`, the example documents, the release asset list, or the stdout of real offline commands disagree, and a CLI unit test compares an emitted envelope with the schema file's `const`.

The reset line was not frozen at 834d8466. Its schema changed again in 02ad8e80, 2b544193, e32d6764, and 4766fe78, so `schemas/historical/packetcraftr.output.v1-reset-4766fe78.schema.json` keeps its final state byte for byte, including its original `$id`. Earlier reset-line drafts remain only in git. The archived file exists for provenance and is never shipped in release archives, which carry only the current schema.

New output uses only `packetcraftr.output/v19`, and the scan-diff and report inputs, like the reference forwarding consumer, accept nothing else. A `packetcraftr.output/v1` document is ambiguous because the released 0.3.0 to 0.5.0-beta.2 line gave each release its own v1 schema and the unreleased reset line reused the identifier with an incompatible one. Development builds between those tags also changed the v1 schema without changing the identifier. Validating such a document needs release provenance, meaning the version of the release that produced it and the schema archived with that release. Our consumers reject it with an error that asks for the input to be regenerated with the current release, and they never validate it against whichever schema happens to be present. Identifiers v2 through v18 each name a single contract line on the main branch, so the identifier alone is enough to pick the schema listed above. Only v2 was released, in 0.5.0-beta.3, and v3 through v18 existed only in development builds. Several of them changed content while under development, and v2, v7, v8, and v18 also have drafts on unmerged branches, so a document from a development build should be checked against the schema at the commit that produced it.

The published surface is one explicit boundary. Machine-readable problem codes are variants of the typed `Code` enum in `crates/packetcraftr-core/src/error/code.rs`, and each variant's `as_str` is the only spelling an envelope may carry. Internal structures reach output only through the CLI's own output types under `crates/packetcraftr-cli/src/output/`, converted field by field from internal values. `scripts/check_output_schema.py` validates every `code` in example and runtime documents against the closed set of codes the Rust sources declare, so a new published code is a deliberate addition to that set rather than a side effect of an internal rename.
