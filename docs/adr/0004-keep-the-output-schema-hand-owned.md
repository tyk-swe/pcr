# Keep the output schema hand-owned, checked against a type registry

The output contract in `schemas/packetcraftr.output.v19.schema.json` is hand-written and hand-maintained next to the Rust output types, which live in `crates/packetcraftr-cli/src/output/` when shared and in a command's `output` module otherwise. We spiked generating it from those types with schemars 0.9, deriving schemas for faithful miniatures of a flattened aggregate report, an untagged stream event enum, a report with `skip_serializing_if` options and a constant-valued `method` field, and an internally tagged enum. The generated schemas do not reproduce v19 semantics. A constant-valued `&'static str` field comes out as a plain string where v19 pins a `const`. An option skipped when absent comes out as a nullable type where v19 admits the field only when present. A `u64` comes out with no maximum where the shared `uint64` definition pins the full range, and `bytes_hex` loses the `hexBytes` pattern. Untagged enums come out as a bare `anyOf` where v19 discriminates stream records with per-event `const` values under a `oneOf`. The envelope fields themselves, such as `command`, `event`, `mode`, and `schema`, are injected by the stream encoder and appear in no published type, so no type-driven generator can produce the envelope layer at all. We therefore keep the schema hand-owned.

What stops the two sides drifting is now explicit. The `PUBLISHED_TYPES` registry in `crates/packetcraftr-cli/src/output/contract.rs` names, for every aggregate and stream envelope definition and every command that publishes it, the Rust types that serialize to it, the stream events they emit, and one checked-in example. `scripts/check_output_schema.py` fails when a registry row names a definition or type that no longer exists, when its events disagree with the definition, when no example record validates against the definition, when a definition or command goes unclaimed, or when a stream record type appears in the sources without a registry row. The schema stays the normative document and the registry stays a checked index into it, so internal fields still reach the published surface only through the CLI output types named there.

A future generator could replace the hand-written definitions only by reproducing v19 semantics exactly. That means constant-valued fields, absent-or-present options without null, bounded integers, closed objects, string patterns, and the encoder-injected envelope discriminators. The proof we would accept is the existing checker passing against the untouched v19 file and the whole example corpus with the generated schema swapped in, plus a semantic diff showing no document the generated schema accepts that v19 rejects, and none it rejects that v19 accepts.
